# AD-147 — Claude Code's adapter dropped tool output for shell and MCP events, so enforce mode remembered nothing

- **status**: active

## Decision

1. **The `tool_response` mapping moves out of the `tool.before | tool.after | tool.failure` branch** in
   `src/providers/claude/claude.inbound.ts` and runs before the switch, for every event kind. A payload that
   carries no such field is unaffected, so nothing else changes.
2. **`post-tool-use-bash.json` and `post-tool-use-mcp.json` gain the `tool_response` a real payload carries.**
   Both fixtures predated anything reading the field.
3. **Three tests**: `shell.after` carries what the command returned, `mcp.after` carries what the server
   returned, and — the one that matters — a `Bash` `curl` payload run through `claudeToEvent` into
   `rememberUntrustedOutput` fills the recall that `askIfFromUntrusted` then matches against.

## Why

**Found live, not by reading.** On a machine with `untrustedContent` enabled in `enforce` mode, the framing
message fired on a `curl` — and no recall file had ever been written, on any session. The framing half calls
`detectUntrustedRead` and needs no output; the remembering half returns early when `toolOutput` is `undefined`
(`untrusted.service.ts:83`). So the visible half worked and the half that can refuse something had no input.

**The cause is the fan-out.** `PostToolUse` is dispatched by tool name: `Bash` → `shell.after`, `mcp__*` →
`mcp.after`, `Edit`/`Write` → `edit.after`, everything else → `tool.after`
(`POST_TOOL_USE_FAN_OUT`). The output mapping sat inside the `tool.*` case, which only the fallback reaches.
So the field survived for `WebFetch` and `WebSearch` and was dropped for every shell read and every MCP result.

**That is two of the three source classes the capability documents.** `DEFAULT_UNTRUSTED_COMMAND_PATTERNS`
lists `gh pr view`, `gh pr diff`, `gh pr list`, `gh issue view`, `gh issue list`, `gh api`, `curl` and `wget`,
and `detectUntrustedRead` has a `shell.after` branch written for exactly them. None of it could ever fire on
this host. The catalog entry's claim that tool output is "measured present on Claude Code's PostToolUse" was
true of the event it was measured on and false of the two this rail also needs.

**Cursor was never affected**, which is why this survived. `cursor.inbound.ts:168-171` maps its own `output`
field on `shell.after`, and the capability's own text cites `afterShellExecution` and `afterMCPExecution` as
measured. One adapter translated the field and the other did not, for the same core contract — the exact
divergence [/decisions/ad-004.md](/decisions/ad-004.md) exists to prevent.

**Each half had green tests.** The adapter's suite asserted the fan-out and the fields it mapped; the rail's
suite asserted remembering and matching against synthetic events it built itself. Neither asserted the join, so
the field between them could go missing with everything still green. The third test added here is that join,
and it fails against the previous adapter.

**This is the [/decisions/ad-076.md](/decisions/ad-076.md) shape.** A control reporting as enabled while
checking nothing is worse than no control, because the operator has stopped looking. `doctor` said the rail was
on, the framing appeared every turn, and the enforce half had no input on the majority of the sources it names.

## Trade-offs

**More content now reaches the recall on Claude Code, which is the point and also a cost.** Every `curl`,
`wget`, `gh` read and MCP result in an `enforce`-mode session is now remembered, bounded at 64 KB per session
by `RECALL_BUDGET_CHARS` with the oldest dropped first. That is the behaviour the capability always described,
and on this host it is new load: more state written per turn, and more content for the verbatim check — and,
where `untrustedContent.judge` is enabled, more entries to send and pay for
([/decisions/ad-146.md](/decisions/ad-146.md)).

**The verbatim rail will now ask about things it never asked about before on Claude Code.** An operator whose
session reads a README with `curl` and then runs a command printed in it gets an `ask` that did not exist
yesterday. That is the rail working as documented, and it will still read as a behaviour change.

**`event.toolOutput` is now set on any event kind whose payload carries `tool_response`**, including
`edit.after` and `read.before`, where nothing reads it today. Harmless, and it is the price of not re-deriving
the field per branch — the alternative is a list of kinds that has to be updated whenever the fan-out changes,
which is the failure this record is about.

## Not decided here

- **Whether the catalog entry's measurement claim should be reworded.** It says tool output is "measured
  present on Claude Code's PostToolUse", which was measured on `tool.after` and is now true of all three. The
  sentence is no longer misleading, so it is left alone rather than rewritten to describe a defect that no
  longer exists.
- **Whether `docs/coverage.md`'s ASI01 row changes.** Its limit is about rewritten commands and shell-only
  scope, neither of which this record touches.
- **Whether other adapters drop other fields the same way.** This record fixes the one field found missing by
  a live observation. A check that joins every adapter's mapping to what core actually reads is the general
  form, and `tools/dev/check-wiring.ts` is where it would live.
- **Whether the recall should be populated from `shell.before`'s own command output.** There is none at that
  point; the read has not happened yet.
